# pm-board

**커밋을 읽어 스스로 갱신되는 로컬 칸반 진행 보드입니다.**

일감을 사람이 끌어 옮기지 않습니다. 커밋 제목에 작업 코드를 붙여 두면
스크립트가 그것을 읽어 단계를 완료로 바꾸고, 일감이 설 칸을 다시 계산합니다.

```
기획  →  개발  →  QA  →  릴리즈 대기  →  배포 완료
PL       FE·BE   QA     RL(대기)        RL(완료)
```

- 서버가 없습니다. HTML 파일 하나와 Node 스크립트 넷이 전부입니다.
- 데이터는 `pm/kanban.json` 하나입니다. 프로젝트 저장소 안에 같이 들어갑니다.
- 그래서 진행 상황이 코드와 같은 이력에 남고, 되돌릴 수 있습니다.

## 무엇이 필요한가

| 항목 | 조건 |
|---|---|
| 브라우저 | Chrome 또는 Edge |
| Node.js | 18 이상 |
| 저장소 | git 저장소 안에서 씁니다 |

⚠️ 보드 화면은 로컬 폴더에 직접 읽고 쓰는 브라우저 기능(File System Access API)을 씁니다.
Safari 와 Firefox 에서는 열리지 않습니다.

## 설치

이 저장소의 `pm/` 폴더를 **쓰려는 프로젝트의 최상위**에 통째로 복사합니다.

```
내-프로젝트/
├─ src/
├─ package.json
└─ pm/            ← 여기에 복사
   ├─ kanban.json
   ├─ kanban.html
   ├─ sync-commits.js
   ├─ preflight.js
   ├─ make-report.js
   └─ lock.js
```

스크립트는 자기 위치의 한 단계 위를 프로젝트 최상위로 봅니다.
그래서 `pm/` 이 최상위에 있어야 git 이력을 제대로 읽습니다.

프로젝트의 `package.json` 에 `"type": "module"` 이 없으면 넣어 주세요.
`.gitignore` 에 `pm/kanban.lock` 을 한 줄 넣어 주세요.

## 처음 한 번 설정

`pm/kanban.json` 을 열어 세 곳을 자기 프로젝트에 맞춥니다.

```json
{
  "project": "내 프로젝트",
  "repoUrl": "https://github.com/내계정/내레포",
  "branches": { "main": "main", "work": "feature" }
}
```

| 항목 | 뜻 |
|---|---|
| `project` | 보고서 제목에 쓰입니다 |
| `repoUrl` | 커밋 해시가 링크로 바뀝니다. 비우면 글자로만 나옵니다 |
| `branches.main` | 배포되는 가지 |
| `branches.work` | 개발이 커밋하는 가지. `main` 하나만 쓰면 둘을 같게 적습니다 |

들어 있는 일감 4개는 **도구가 어떻게 도는지 보이려고 넣은 예시**입니다.
`jobs` 를 비우고 `sections` 를 자기 화면 구조로 바꿔 쓰십시오.

## 쓰는 법

### 1. 보드 열기

`pm/kanban.html` 을 브라우저로 엽니다. 처음 한 번 **프로젝트 최상위 폴더**를 고르라고 합니다.
한 번 고르면 다음부터 기억합니다.

### 2. 일감 만들기

보드에서 일감을 추가하면 작업 코드가 자동으로 붙습니다.

```
PL-1.2   기획
FE-1.2   클라이언트 (화면에 보이는 것)
BE-1.2   서버 (눈에 안 보이는 로직)
QA-1.2   검증
RL-1.2   릴리즈
```

### 3. 커밋 제목 끝에 작업 코드를 붙입니다

```
feat(로그인): 아이디 저장 체크박스 [FE-1.2]
fix(발송): 재시도 간격 계산 오류 [BE-1.4]
```

⚠️ **반드시 대괄호 안에 넣습니다.** 스크립트는 대괄호에 든 것만 읽습니다.
한 커밋이 여러 일감에 걸리면 여러 개 적습니다. `[FE-1.7] [FE-1.8]`

### 4. 붙이고 새로고침

```
node pm/sync-commits.js           무엇이 안 붙었는지 본다 (안 고침)
node pm/sync-commits.js --write   실제로 붙인다
node pm/make-report.js --write    pm/진행표.md 를 다시 쓴다
```

⚠️ **보드가 브라우저에 열려 있는 채로 `--write` 를 돌리지 마세요.**
열린 화면은 파일이 밖에서 바뀐 것을 모릅니다. 돌렸으면 F5 로 다시 읽습니다.

## 배포 전 점검

```
node pm/preflight.js           지금 상태로 점검한다
node pm/preflight.js --fetch   원격을 먼저 받아 온 뒤 점검한다
```

아홉 가지를 보여 줍니다. **아무것도 고치지 않고, 배포를 막지도 않습니다.**
종료 코드는 늘 0 입니다. 판단은 사람이 합니다.

```
① 나갈 커밋        ⑥ 칸 자리
② 릴리즈 대기      ⑦ 상태값
③ 섞여 나갈 코드   ⑧ 로컬과 원격
④ 정리 안 된 커밋  ⑨ 마지막 태그
⑤ 미커밋 파일
```

③이 핵심입니다. 검증이 안 끝났는데 코드가 바뀌는 커밋이 이번 배포에 섞여 나가는지 보여 줍니다.
문서만 바뀐 커밋은 따로 세어 뺍니다. 안 가르면 매번 전부가 경고로 떠서, 늘 걸리는 경고가 되고
그러면 아무도 안 보게 됩니다.

⚠️ 문서로 치는 폴더는 `pm/` 과 `docs/` 입니다. 프로젝트마다 다르므로
`preflight.js` 와 `sync-commits.js` 의 `DOC_DIRS` 를 자기 저장소에 맞추십시오.
**두 파일의 목록이 같아야 합니다.**

## 명령 모음

```
npm run sync          커밋이 어디에 붙을지 본다 (안 고침)
npm run sync:write    실제로 붙인다
npm run report        pm/진행표.md 를 다시 쓴다
npm run preflight     배포 전 아홉 가지를 점검한다
```

## 알아 둘 것

- **`git reflog` 를 씁니다.** 배포 시각과 태그를 여기서 읽는데, reflog 는 그 컴퓨터에만 있습니다.
  다른 기기에서 돌리면 배포 완료로 안 넘어갑니다. 그때는 원래 컴퓨터에서 한 번 돌리면 됩니다.
- **여러 사람이 같은 파일을 고칩니다.** 겹치지 않게 `pm/kanban.lock` 잠금과
  `updatedAt` 대조를 두 겹으로 걸어 두었습니다. 자세한 것은 기능정의서를 보십시오.
- **QA 만 상태가 넷입니다.** 고친 사람과 검증하는 사람이 다르기 때문입니다.
  `수정 완료` 는 아직 검증 전이고, `검증 완료` 여야 다음 칸으로 넘어갑니다.
