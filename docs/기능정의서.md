# pm-board 기능정의서

이 문서가 **로직의 정본**입니다. 코드 주석과 어긋나면 이 문서를 따릅니다.

---

## 1. 무엇을 푸는가

진행 관리 도구는 대개 **사람이 카드를 옮겨야** 상태가 맞습니다.
옮기는 것을 잊으면 보드가 실제와 어긋나고, 어긋난 보드는 아무도 안 보게 됩니다.

이 도구는 **커밋을 근거로 삼습니다.** 커밋 제목 끝에 작업 코드를 붙여 두면
스크립트가 그것을 읽어 단계를 완료로 바꾸고, 일감이 설 칸을 다시 계산합니다.

| 무엇이 근거인가 | 어디서 읽나 |
|---|---|
| 단계가 끝났나 | 그 단계 코드가 붙은 커밋이 있나 |
| 배포됐나 | 그 일감의 커밋이 전부 `origin/<main>` 에 있나 |
| 언제 배포됐나 | `git reflog show origin/<main>` 의 push 시각 |
| 어떤 태그로 나갔나 | 그 push 커밋을 가리키는 태그 |

## 2. 데이터 구조

정본은 `pm/kanban.json` 하나입니다.

```
kanban.json
├─ project        보고서 제목에 쓰인다
├─ docVersion     이 보드의 판 번호. 사람이 적는다
├─ intro          보드 맨 위에 나오는 설명
├─ repoUrl        커밋 링크의 앞부분. 비우면 해시가 글자로만 나온다
├─ branches       { main: "main", work: "feature" }
├─ updatedAt      마지막 저장 시각. 덮어쓰기를 막는 열쇠다
├─ legend.areas   PL·FE·BE·QA·RL 이 무엇인지
├─ sections[]     섹션(메뉴 그룹) > screens[](화면)
├─ jobs[]         일감
├─ ui             화면 글자를 바꾸고 싶을 때만 채운다
├─ syncSince      이 커밋 "다음"부터 검사한다. 비우면 전체
├─ unlinked       코드가 안 붙은 커밋 목록 (스크립트가 적는다)
└─ ignoredCommits 일부러 안 붙이기로 한 커밋 (사람이 이유와 함께 적는다)
```

### 일감 하나

```json
{
  "no": "1.2",
  "sec": "1",
  "screen": "회원 가입",
  "title": "가입 화면 만들기",
  "dev": "FS",
  "col": "dev",
  "steps": {
    "plan":    { "code": "PL-1.2", "status": "done",  "doneAt": "2026-01-08", "commits": [] },
    "fe":      { "code": "FE-1.2", "status": "doing", "doneAt": null,         "commits": [] },
    "be":      { "code": "BE-1.2", "status": "block", "doneAt": null,         "commits": [] },
    "qa":      { "code": "QA-1.2", "status": "idle",  "doneAt": null,         "commits": [] },
    "release": { "code": "RL-1.2", "status": "idle",  "doneAt": null,         "commits": [] }
  }
}
```

- `sec` 는 `sections[].no` 와, `screen` 은 그 섹션의 `screens[].name` 과 맞아야 합니다.
- `dev` 는 `FE` · `BE` · `FS`(둘 다) 셋 중 하나입니다. 배지로 보입니다.
- `col` 은 **스크립트가 계산해 넣습니다.** 사람이 적지 않습니다.
- 단계 키는 `plan` · `fe` · `be` · `qa` · `release` 다섯입니다.
  **필요 없는 단계는 키 자체를 두지 않습니다.** 위 예시에는 `be` 가 있고, FE 만 하는 일감에는 없습니다.

### 단계 하나가 갖는 것

| 칸 | 뜻 |
|---|---|
| `code` | `영역-화면번호.순번`. 커밋 제목에 적는 그것 |
| `title` | 짧은 이름 |
| `desc` | 무엇을 왜 하는지. 길게 적어도 됩니다 |
| `ref` | 참고 자료 (파일명·문서명) |
| `status` | 아래 4절 |
| `doneAt` | 완료일. **마지막 커밋 날짜**입니다 |
| `commits` | 붙은 커밋 해시 |
| `includes` | 이 커밋에 함께 나간 다른 작업 |
| `rounds` | QA · RL 에만. 아래 6절 |

릴리즈 단계는 셋을 더 갖습니다.

```
shippedCommit   그 배포의 머지 커밋
shippedAt       push 시각
shippedTag      그 배포의 태그
```

## 3. 칸 계산 규칙

**일감이 설 칸은 단계 상태에서 자동으로 나옵니다.** 위에서부터 처음 걸리는 것이 답입니다.

```
plan 이 있고 안 끝났다            → 기획
fe 나 be 중 하나라도 안 끝났다     → 개발
qa 가 없거나 안 끝났다             → QA
release 가 없거나 안 끝났다        → 릴리즈 대기
전부 끝났다                       → 배포 완료
```

- **기획으로 끝나는 일감**(코드가 안 바뀌는 결정 사항 등)은 `fe`·`be` 키를 두지 않습니다.
  개발 칸에서 멈추지 않고 바로 QA 로 갑니다.
- ⚠️ **`qa` 나 `release` 키가 없으면 그 칸에 영원히 섭니다.** 다섯 칸을 다 지나게 하려면
  네 단계가 다 있어야 합니다.

### 끝났다의 뜻

```
status 가 'done' 이고,
rounds 가 있으면 그 회차가 전부 'done' 이다
```

회차가 하나라도 안 끝나면 그 단계는 안 끝난 것입니다.

## 4. 상태값

네 칸(`plan` · `fe` · `be` · `release`)은 넷입니다.

| 값 | 화면 글자 |
|---|---|
| `idle` | 대기 |
| `doing` | 진행 중 |
| `done` | 완료 |
| `block` | 보류 |

**QA 만 다섯입니다.** 고친 사람과 검증하는 사람이 다르기 때문입니다.

| 값 | 화면 글자 | 언제 | 누가 찍나 |
|---|---|---|---|
| `idle` | 대기 | 볼 것이 정해졌다 | 사람 |
| `doing` | 진행 중 | 수정 개발이 시작됐다 | 사람 |
| `fixed` | 수정 완료 | 고치기가 끝났다. **아직 검증 전이다** | 스크립트 |
| `done` | 검증 완료 | 화면을 보고 컨펌했다 | 사람 |
| `block` | 보류 | 세워 두었다 | 사람 |

⚠️ **`sync-commits.js` 는 QA 를 검증 완료로 못 찍습니다.**
커밋은 "고쳤다" 는 기록이지 "검증했다" 는 기록이 아닙니다. `fixed` 까지만 올립니다.
**`done` 일 때만 다음 칸으로 넘어갑니다.**

> 이 값이 없던 때는 수정 개발이 끝나면 곧바로 릴리즈 대기로 넘어갔습니다.
> 검증을 안 했는데 배포 줄에 선 것입니다. `fixed` 가 그 사이를 막습니다.

⚠️ 이미 `done` 인 것을 스크립트가 `fixed` 로 내리지 않습니다.
내리면 돌릴 때마다 검증이 풀립니다.

## 5. 작업 코드 규칙

```
feat(로그인): 아이디 저장 체크박스 [FE-1.2]
fix(발송): 재시도 간격 계산 오류 [BE-1.4]
```

- 영역은 `PL` · `FE` · `BE` · `QA` · `RL` 다섯 중 하나입니다.
- **반드시 대괄호 안에 넣습니다.** 스크립트가 읽는 정규식이 대괄호를 요구합니다.

```
/\[(PL|FE|BE|QA|RL)-(\d+)\.(\d+)(?:\.(\d+))?\]/g
```

- 한 커밋이 여러 일감에 걸리면 여러 개 적습니다. `[FE-1.7] [FE-1.8]`
- 코드가 없는 커밋은 **"정리 안 된 커밋"** 으로 보드에 뜹니다.
  없애는 장치가 아니라 **빠뜨림을 눈에 보이게 하는 장치**입니다.
- 보드에 없는 코드로 커밋하면 **"칸반에 없는 코드"** 로 뜹니다. 일감을 먼저 만들고 커밋합니다.

### 일부러 빼는 목록

갈 곳이 정말 없는 커밋은 `ignoredCommits` 에 **이유와 함께** 적습니다.

```json
{ "hash": "47aa645", "at": "2026-09-02", "by": "PM",
  "why": "그 일감이 다른 일감으로 병합되며 코드 자체가 사라져 붙일 칸이 없다." }
```

⚠️ **남용하면 장치가 죽습니다.** 아직 안 붙였을 뿐인 커밋은 넣지 않습니다.
그것은 일감을 만들어 붙일 일입니다.
숨기되 없애지는 않습니다. 몇 건을 뺐는지 스크립트가 끝에 늘 한 줄로 보여 줍니다.

## 6. QA · RL 회차

QA 를 한 번에 통과하면 `QA-1.2` 하나로 끝납니다.
**되돌아와 다시 고치면** 그 회차를 셋째 자리로 매겨 QA 칸 안에 쌓습니다.

```
QA-1.2      1회차
QA-1.2.1    2회차
QA-1.2.2    3회차
```

- **`.1` 이 2회차입니다.** 1회차에는 셋째 자리를 안 붙입니다.
- 회차마다 **그 회차에서 새로 고친 내용**을 적습니다. 앞 회차 글을 고쳐 쓰지 않습니다.
  무엇이 몇 번 되돌아왔는지가 남아야 합니다.
- ⚠️ **셋째 자리는 QA 와 RL 에만 씁니다.** `PL` · `FE` · `BE` 는 두 자리입니다.
  `FE-1.2.1` 로 커밋하면 스크립트가 읽기를 거부합니다.

### 릴리즈 회차는 짝으로 생깁니다

`main` 에 나간 뒤 QA 로 되돌아와 고치고 다시 나가면 **그것은 두 번째 배포**입니다.
배포마다 커밋·시각·태그가 다르므로 릴리즈 칸에도 회차를 쌓습니다.

```
RL-1.6      1차 배포   572506b   2026-08-28   v1.4.0
RL-1.6.1    2차 배포   9f3a21c   2026-08-31   v1.5.0
```

⚠️ **QA 회차를 만들면 릴리즈 회차가 짝으로 함께 생깁니다.** `대기` 상태로 섭니다.
QA 가 되돌아왔다는 것은 고친 것을 **다시 배포해야 한다**는 뜻이기 때문입니다.

> 짝이 없던 때 QA 회차를 완료로 바꾸자, 옛 릴리즈가 완료라서 그 일감이 곧바로
> **배포 완료**로 갔습니다. 고친 것은 아직 개발 가지에만 있었습니다.

⚠️ **릴리즈 회차의 상태는 사람이 안 바꿉니다.** `sync-commits.js` 가 reflog 를 읽어
`대기` 를 `완료` 로 바꾸고 태그를 적습니다. 릴리즈 칸에는 회차 추가 버튼이 없습니다.

## 7. `sync-commits.js` 가 하는 일

```
node pm/sync-commits.js                    본다 (아무것도 안 고침)
node pm/sync-commits.js --write            고친다
node pm/sync-commits.js --write --as PO    잠금에 이름을 남긴다
```

도는 순서입니다.

```
① 잠금을 잡는다 (--write 일 때만)
② kanban.json 을 읽고 updatedAt 을 기억한다
③ syncSince 다음부터 커밋 로그를 읽는다
④ 제목에서 작업 코드를 뽑아 그 단계에 커밋을 붙인다
⑤ 그 단계를 완료로 찍는다 (QA 는 수정 완료까지)
⑥ main 에 나간 일감의 릴리즈 칸을 완료로 찍고 태그를 적는다
⑦ 칸 자리를 다시 계산한다
⑧ updatedAt 이 그대로면 저장한다. 달라졌으면 아무것도 안 고치고 멈춘다
⑨ 잠금을 푼다
```

### 완료일은 마지막 커밋 날짜입니다

관련 커밋이 한 번 더 나면 완료일도 그날로 **갱신됩니다.**
그러면 그 일감은 어제 목록에서 빠져 오늘 목록으로 옮겨 갑니다. 그것이 맞습니다.
뒤에 또 손댔다는 것은 그날 다시 일한 것이고, 보고는 그 사실을 보여야 합니다.

### 완료로 안 찍는 두 경우

| 무엇 | 왜 |
|---|---|
| 보류(`block`)로 세워 둔 단계 | 사람이 일부러 세웠습니다 |
| 진행 데이터만 바꾼 커밋 | 일을 한 것이 아니라 기록만 한 것입니다 |

두 번째는 `RECORD_FILES`(`pm/kanban.json` · `pm/진행표.md`)만 바뀐 커밋입니다.
이 구분이 없으면 **일감을 등록한 커밋이 그 일감을 곧바로 완료로 찍습니다.**

### 배포 판정

그 일감의 커밋이 **전부** `origin/<main>` 에 있고, 릴리즈 말고 나머지 칸이 다 끝났으면
릴리즈 칸을 완료로 찍습니다.

- ⚠️ 안 끝난 칸이 하나라도 남아 있으면 안 찍습니다. 그 조건이 없으면 대기인 일이 완료가 됩니다.
- ⚠️ **문서만 바꾼 커밋은 뺍니다.** 안 빼면 그 커밋이 실린 나중 push 가 재배포로 잡힙니다.
- 같은 push 를 두 번 적지 않으므로 몇 번을 돌려도 결과가 같습니다.

## 8. `preflight.js` 아홉 항목

```
node pm/preflight.js           지금 상태로 점검
node pm/preflight.js --fetch   원격을 받아 온 뒤 점검
```

| 무엇 | 왜 보나 |
|---|---|
| ① 나갈 커밋 | `origin/<main>..origin/<work>` 몇 건인가 |
| ② 릴리즈 대기 | 이번에 내보낼 일감 |
| ③ 섞여 나갈 코드 커밋 | **검증 안 끝났는데 코드가 바뀌는 커밋** |
| ④ 정리 안 된 커밋 | 작업 코드가 없는 커밋 |
| ⑤ 미커밋 파일 | 다른 사람이 작업 중인가 |
| ⑥ 칸 자리 | `sync-commits.js` 를 안 돌렸는가 |
| ⑦ 상태값 | **정의에 없는 값이 들어갔는가** |
| ⑧ 로컬과 원격 | 안 올린 커밋이 있는가 |
| ⑨ 마지막 태그 | 다음 태그 제안 |

- ③이 핵심입니다. **문서만 바뀐 커밋은 따로 세어 뺍니다.** 안 가르면 매번 커밋 전부가
  경고로 떠서 **늘 걸리는 경고가 되고, 그러면 안 보게 됩니다.**
- ⚠️ **이 점검은 배포를 막지 않습니다.** 종료 코드는 늘 `0` 입니다.
  섞이는 일은 늘 있으므로 막으면 무시하게 됩니다. 판단은 사람이 합니다.
- ⑦은 정의에 없는 상태값을 찾습니다. 낯선 값은 `idle` 과 같게 취급되어
  **칸 자리가 안 틀어진 채 조용히 지나갑니다.**
- ⑨의 태그 제안은 나갈 커밋에 `feat(` 가 있는지로 갈립니다. 정하는 것은 사람입니다.

## 9. `make-report.js`

`pm/kanban.json` 에서 사람이 읽는 `pm/진행표.md` 를 만듭니다.

```
node pm/make-report.js --write
```

- JSON 은 `git diff` 로 안 읽힙니다. 무엇이 바뀌었는지 보이려고 만듭니다.
- ⚠️ **손으로 고치지 않습니다.** 다음 실행 때 덮어써집니다. 정본은 `kanban.json` 입니다.
- 이 스크립트는 **읽기만 하므로 잠금을 잡지 않습니다.**

## 10. 동시 편집 막기

여러 사람이 같은 `kanban.json` 을 고칩니다. 스크립트로도 고치고 브라우저로도 고칩니다.
겹치면 나중에 저장한 쪽이 먼저 것을 덮어씁니다.

### 잠금 파일은 따로 둡니다

```
pm/kanban.lock
{ "by": "PM", "id": "l8f3k2a9", "at": "2026-09-01T09:12:00.000Z" }
```

⚠️ **잠금을 `kanban.json` 안에 두지 않습니다.** 잠금을 잡는 행위가 곧 그 파일을 쓰는
것이라, 두 쪽이 같이 "비어 있네" 하고 각자 써 버리면 막으려던 사고가 그대로 납니다.
**지키려는 파일과 잠금 파일을 가릅니다.**

`id` 는 이번에 잡은 것만 가리키는 표입니다. 쓴 뒤 다시 읽어 내 `id` 가 남아 있어야
내가 이긴 것입니다.

### 도는 순서

```
① 잠금을 읽는다
② 남이 잡았고 20초가 안 지났으면 → 0.3초마다 풀렸는지 다시 본다 (최대 1분)
③ 비었거나 20초가 지났으면 → 내 것으로 쓰고, 0.15초 뒤 다시 읽어 내 것인지 확인
④ 내 것이면 kanban.json 을 읽고 · 고치고 · 쓴다
⑤ 끝나면 잠금을 지운다 (내 것일 때만)
```

| 상수 | 값 | 왜 |
|---|---|---|
| `TTL` | 20초 | 지나면 멈춘 것으로 보고 뺏습니다. 실측 2초짜리 작업이라 여유가 넉넉합니다 |
| `SETTLE` | 150ms | 쓰고 나서 다시 읽기까지 |
| `POLL` | 300ms | 풀렸는지 다시 보는 간격 |
| `WAIT_MAX` | 60초 | 이만큼 기다려도 못 잡으면 포기하고 사람에게 알립니다 |

### `updatedAt` 이 마지막 관문입니다

잡고 있는 동안에도 만료로 뺏길 수 있고, 그때 상대가 파일을 고칩니다.
그래서 **쓰기 직전에 `updatedAt` 이 열 때와 같은지 다시 봅니다.** 달라졌으면 안 쓰고 멈춥니다.

```
화면      파일이 밖에서 바뀌었습니다. F5 로 다시 읽어 주세요
스크립트  돌리는 사이에 kanban.json 이 밖에서 바뀌었습니다. 아무것도 안 고쳤습니다
```

잠금은 겹칠 자리를 줄이고, `updatedAt` 은 그래도 겹쳤을 때 덮어쓰기를 막습니다. 두 겹입니다.

⚠️ **읽기만 하는 실행은 잠그지 않습니다.** `--write` 없는 실행과 `make-report.js` 가 그렇습니다.

## 11. 같은 규칙이 두 벌 있는 자리

브라우저는 로컬 모듈을 못 부르므로 화면과 스크립트에 같은 코드가 한 벌씩 있습니다.
**한쪽만 고치면 화면과 데이터가 갈립니다.**

| 무엇 | 어디 | 어디 |
|---|---|---|
| 잠금 | `pm/lock.js` | `kanban.html` 의 `lockAcquire` |
| 칸 계산 | `sync-commits.js` 의 `colOf` | `kanban.html` 의 `colOf` |
| 끝났나 | `sync-commits.js` 의 `isDone` | `kanban.html` 의 `isDone` |
| 문서 폴더 | `sync-commits.js` 의 `DOC_DIRS` | `preflight.js` 의 `DOC_DIRS` |

잠금은 **값(20초 · 150ms · 300ms · 60초)과 순서가 같아야** 서로를 알아봅니다.

## 12. 한계

- **`git reflog` 에 기댑니다.** 배포 시각과 태그를 여기서 읽는데, reflog 는 그 컴퓨터에만
  있습니다. 다른 기기에서 돌리면 이 단계가 조용히 비어 배포 완료로 안 넘어갑니다.
  그때는 원래 컴퓨터에서 한 번 돌리면 됩니다.
- **브라우저가 갈립니다.** 로컬 폴더에 직접 쓰는 기능이 Chrome 계열에만 있습니다.
- **커밋 제목은 나중에 고칠 수 없습니다.** 코드를 잘못 적었으면 그 커밋은 영영 그대로입니다.
  그래서 `ignoredCommits` 가 있습니다.
- **`syncSince` 앞은 다시 안 봅니다.** 옛 커밋을 다시 훑으면 지금 규칙과 다르게 적힌
  옛 커밋이 엉뚱한 일감에 붙습니다.
